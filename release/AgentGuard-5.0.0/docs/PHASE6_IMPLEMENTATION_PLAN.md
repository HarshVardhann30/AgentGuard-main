# AgentGuard Phase 6 Implementation Plan

## Repository audit (2026-10-27)

### Architecture found

- `agent/agent.py`: existing synchronous Ollama `Agent.run` loop. It reads the single `agent.tools.TOOL_REGISTRY`, calls `security.guard.AgentGuard.execute`, returns truthful execution results, and stops when audit persistence fails. Preserve this loop and the dashboard contract.
- `agent/tools.py`: the authoritative tool registry and implementations. It currently includes `read_file`, `calculator`, `write_file`, and several existing tools; the registry schema uses `{function, description, parameters, ...}`. File tools confine paths to `data/document`; writes and copy/move/delete carry a mandatory minimum REVIEW policy.
- `security/guard.py`: the one authoritative execution boundary. Its flow is schema/type validation and deterministic `mandatory_denial`, history and `RiskPredictor` inference, hybrid `security.risk.assess`, ALLOW/REVIEW/BLOCK threshold and minimum-decision resolution, durable pre-execution authorization audit for ALLOW, pending approval persistence without execution for REVIEW, and protected tool invocation with completion audit. Approval atomically claims a request and revalidates identity, hash, expiry, policy, arguments, target, rules, and risk.
- `security/rules.py`, `security/risk.py`, `ml/features.py`, `ml/policy.py`, and `ml/predictor.py` are separate mandatory-rule, behavioral, feature, threshold, and learned-model modules. Missing/incompatible model or failed persistence blocks. Do not let a learned score override the deterministic rules or per-tool minimum decision.
- `security/logger.py` writes redacted JSONL and calls the configured SQL persistence sink. `backend/database.py` and `backend/models.py` persist actions, task/session IDs, separate model and hybrid-risk fields, security events and approvals. Existing SQLite `data/agentguard.db` and JSONL logs are runtime/user data and must not be used for destructive evaluation.
- `backend/main.py`: FastAPI serves task, action, event, session, approval, settings, model, and health APIs. The background task constructs the existing Ollama Agent with AgentGuard. There is no external-agent API or command today.
- `ml/dataset.py` creates an existing reproducible trace/event dataset; `ml/pipeline.py` fits grouped trace splits and currently trains Random Forest and XGBoost, selects using validation, compares an independent heuristic rule baseline, persists a paired estimator/calibrator artifact and evaluation JSON. The existing dataset is synthetic and the current scenario/trace labels are not an action-level approval ground truth. `ml/artifacts/` contains checked-in-looking generated model/evaluation files, but Python/scikit-learn compatibility must be checked in the active runtime before changing them.
- `frontend/` is Next.js 15/React 19/TypeScript with Vitest tests. Its dashboard reads persisted FastAPI data and `GET /model`; do not present fabricated metrics. Existing action displays distinguish operational risk and ML probability.
- Existing test files cover tools, Ollama agent, guard, approvals, API, SQLite persistence, feature extraction, grouped splits, model serialization and frontend interactions. Python test configuration is pytest. No root pyproject/pytest configuration or CI workflow is present.
- PowerShell setup/start scripts and README are present. `requirements.txt` pins scikit-learn 1.9.1 and XGBoost 3.4.1 but does not yet include AutoGen or a dataset validator.

### AutoGen dependency compatibility research

Official Microsoft AutoGen stable documentation identifies the current stable AgentChat release as 0.7.5 and states Python 3.10+; AgentChat is built on `autogen-core`. Its quickstart installs `autogen-agentchat` with `autogen-ext[openai,azure]`. For this project, use the official `autogen-agentchat==0.7.5`, `autogen-core==0.7.5`, and the OpenAI-compatible provider extra from the same release only if needed. The adapter must remain importable without these optional packages so ordinary Ollama use remains available. Use AutoGen's AgentChat tool representation as a proposal surface only; every callable is an adapter-owned wrapper that invokes the *same* AgentGuard instance. Disable parallel tool execution and configure bounded runtime/timeouts. Do not expose underlying functions as AutoGen tools.

## Integration design and planned changes

1. Add a narrow `agent/autogen_adapter.py` factory/runner. Reuse the project's existing `TOOL_REGISTRY` via AgentGuard; publish only `read_file`, `calculator`, and `write_file`. Generate wrapper signatures from their declared exact string-argument schemas, validate the incoming calls through `AgentGuard.execute`, and return the actual serialized `ExecutionResult`, including status, decision, action ID, execution/audit state, error, agent identity, task/session identity. Configure AutoGen to execute wrappers sequentially. Adapter identity/task/session become the guard identity fields so records and approvals remain bound. REVIEW is reported as pending and never run by the wrapper; human resolution remains the existing FastAPI approval flow. Add a CLI for real AutoGen using the existing local Ollama OpenAI-compatible endpoint, with an explicitly configured model and no token embedded in the project.
2. Extend the existing dataset with an independently labeled, versioned action-security scenario JSONL (`ml/data/phase6_scenarios_v1.jsonl`) of >100 cases, including paired benign/malicious workflow families and explicit synthetic fixture data. Add a validator/generator module/CLI, stable seed and group identifiers; split grouped by scenario family/template at training time. Labels describe ground-truth policy legitimacy/harm, never copy a risk score. Validate required schema, uniqueness, tool/schema values, classes/family counts and split disjointness.
3. Extend existing `ml/features.py` and `ml/pipeline.py` without replacing feature extraction. Preserve the existing estimator/artifact-loading and risk benchmark contract; add Logistic Regression as the requested baseline and Random Forest as the candidate, retain XGBoost as legacy comparison only if useful, and report the existing heuristic risk benchmark independently. Avoid scenario IDs and future outcomes; fit imputation/encoding in training pipelines. Save a separate Phase 6 artifact and report if the existing artifact's sklearn compatibility cannot be established. Compute metrics from held-out results and calibration diagnostics, never assert calibrated without evidence.
4. Add a reproducible comparative evaluator in the existing ML/evaluation area. It uses disposable temporary document roots, isolated temporary SQLite and audit files, and mocked/synthetic-only tools. Run identical scenario inputs through deterministic/risk-only, ML-assisted AgentGuard, and a deliberately unguarded *safe sandbox* of synthetic no-op/read/calculation effects. Verify actual side effects and persisted audits; record errors/timeouts/inconclusive trials. Write JSON, CSV, and Markdown from computed trials, document denominators and metric formulas; never touch the existing DB/log/documents.
5. Add focused adapter, dataset, ML, and evaluation tests following existing pytest fixtures. Frontend changes only if there is a real Phase 6 evaluation contract and measured Phase 6 data available. Any Phase 6 model/dashboard data must distinguish prediction, ML confidence, hybrid risk, policy decision, approval status and execution outcome and label synthetic results.
6. Create `docs/PHASE6.md` with actual PowerShell commands and `reports/PHASE6_ML_EVALUATION.md` / `reports/PHASE6_SECURITY_EVALUATION.md` from actual runs. State each blocked check explicitly. Update dependency constraints surgically, including the pinned official AutoGen package set.

## Risks and compatibility constraints

- Python 3.14/scikit-learn/XGBoost wheel and serialized-estimator compatibility is not established in this checkout. Do not replace the existing artifact; use a distinct Phase 6 output location if retraining succeeds.
- AutoGen `AssistantAgent` normally executes registered tool callables during `run()`. Consequently **every** registered function must be a guard wrapper, not the underlying tool; prohibit parallel calls to avoid concurrent approval/audit ambiguity. Respect tool-call timeouts and return non-success explicitly.
- A protected `write_file` request typically remains pending; the CLI must not secretly approve it. Existing approval API has a shared-token reviewer model and no integrated reviewer interaction in a local CLI.
- The available workspace may lack package downloads, compiler/wheels, Node/npm and live Ollama. Mark affected end-to-end checks unverified rather than infer results.
- Evaluation data is synthetic and code-authored; test-set metrics cannot establish production detection efficacy. Group partitions must keep complete scenario templates/families together.
- Existing runtime DB/log data is ignored and must remain untouched. No Git metadata exists, so source ownership and an original-repo diff cannot be determined; edits are restricted to files changed for Phase 6.
